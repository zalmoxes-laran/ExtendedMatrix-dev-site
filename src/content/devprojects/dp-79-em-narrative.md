desc: "A first-class semantic-narrative object in the EM graph: a NarrativeNode (em.json → RDF) that interleaves authored prose with live references to EM resources — the Harris matrix and epoch slices, US / USV / proxy with their existence certainty, representation models, documents and images, 3D scenes, maps, timelines, tables and queries, and — the part no comparable tool carries — the source-criticism / paradata reasoning itself, rendered inside the story rather than filed as an appendix. Unlike a word processor or a wiki, the narrative is not a frozen blob of HTML: it is a node in the graph, so it stays queryable, versioned and DTC-traceable, and its embeds are references (by stable ID) that update automatically when the reconstruction changes. One narrative source, many outputs: a dynamic/live web viewer, a smart LaTeX projection for scholarly print, semi-static docx/HTML for hand-off, and a Jupyter-notebook rendering for computational readers. EM Narrative is the authored, documentary document that tells how a reconstruction was reasoned and proven; it is distinct from — and composable with — DP-29 (EMN / Narrative Units), which formalises the performative, intangible-heritage layer (dialogues, rituals, characters)."
components:
  - "**NarrativeNode as a first-class graph object.** A NarrativeNode is a node in em.json (projected to RDF as an `E33 Linguistic Object` / `E73 Information Object`, with a dedicated `emn:Narrative` type), carrying metadata (author, license and embargo via DP-32; version; language via DP-63) and an **ordered sequence of blocks**. Because it is a node — not an exported document — the composition itself is knowledge: you can ask *which narratives cite this US*, *which reconstructions have an authored narrative*, *which narratives depend on a source now retracted*; you can version it, diff it, and trace it through the DTC. This is the deliberate contrast with narrative systems that store the authored document as an opaque HTML blob where only the referenced resources — never the composition — remain queryable."
  - "**Blocks: prose + embeds, no copies.** A narrative is an ordered list of blocks. *Prose blocks* hold rich authored text. *Embed blocks* reference an EM resource **by stable ID** (the same reference hinge used elsewhere in the graph) plus a **view-type** that says how it renders. Nothing is duplicated: an embed is a live reference, so when the underlying US, RM, document or 3D scene changes, the narrative reflects it. This keeps the authored document honest — it can never silently drift from the reconstruction it describes."
  - "**Embed view-types** (the depth EM can carry that generic narrative tools cannot): *matrix / epoch slice* (the Harris matrix or a temporal slice); *3D scene / epoch* (an in-line Heriverse / ATON embed — the 3D dimension); *US / USV / proxy* rendered with its **existence certainty** qualia; *representation model / RMDoc*; *document / image* (via the Shelf / acquisition pipeline, IIIF where warranted); *map* (geo), *timeline*, *table / query* (a live interrogation over em.json); *paradata / source-criticism* — the **why** behind an assertion (source → extractor → property) rendered **inside** the narrative as an evidence chain, not attached as a footnote; and a *narrative-unit scene* embed (DP-29), so an authored document can present a performative scene where one is warranted."
  - "**Living, queryable, versioned.** Because embeds are references and the narrative is a node, three properties hold that a document format cannot offer at once: the narrative is **live** (references auto-update), **queryable** (SPARQL over the composition, not only its parts), and **versioned / DTC-traceable** (every authorial state is a graph state). The evidence chain and the uncertainty of a reconstruction become first-class citizens of the story."
  - "**Multi-output projection — one source, many renderings.** The NarrativeNode is authored once and projected to several publication targets, chosen by the audience rather than re-authored per format: **(1) dynamic / live web viewer** — prose + live embeds including in-line 3D (Heriverse / ATON), the reference implementation of StratiGraph T6.3 dissemination that today is missing; **(2) smart LaTeX** — a scholarly-print projection where embeds resolve to figures, matrix diagrams, evidence tables and proper citations, for journal / monograph output; **(3) semi-static docx / HTML** — a self-contained hand-off document (snapshot of embeds at export time) for reviewers, reports and deliverables; **(4) Jupyter notebook** — a computational rendering where embeds resolve to live s3Dgraphy queries and generated figures, so a reader can re-run the analysis behind the prose. The Jupyter target is not new to the EM horizon: it was already anticipated as an analytics surface in DP-21 (EM Meter — Jupyter statistics over the graph) and DP-13 (Virtual SU Sheet), which EM Narrative generalises from *analysis-only* notebooks into a *narrative* notebook that carries prose, evidence and reproducible computation together."
  - "**Authoring in EMStudio.** Composition happens in the EMStudio 2D web editor: a prose editor plus **drag of resources from the graph / Shelf** to create embeds — the familiar authoring gesture, but operating on em.json rather than on triples or on an HTML document. Embed rendering reuses EMStudio's component system, the property-graph analogue of a template system. Two-tier stays intact: the narrative is authored in the property graph and projected to RDF (E33 + reference predicates), never authored triple-first."
  - "**Viewer naming (open).** *EM Narrative* names the authored object and the authoring concept — the term is deliberately kept because it is the clearest name for what this is. The **runtime that plays a narrative** (the dissemination viewer, output target 1) is a distinct thing that may want its own disambiguated name; candidates floated include *storyline*, though the working assumption is that context disambiguates *narrative* well enough that a separate coined term may not be needed. Flagged here as an open decision, not a blocker."
  - "**Relationship to DP-29 (EMN / Narrative Units).** The two narrative concepts are orthogonal and composable. DP-29 formalises **what was lived inside what was built** — the performative, intangible-heritage layer (dialogue lines, ritual acts, characters as USV, the four-axis `tono` / `registro` / `contenuto` / `tempo` schema). EM Narrative is **the document that recounts the reconstruction and its evidence** — an authored, documentary artefact. A DP-29 scene is one of EM Narrative's embed view-types: an EM Narrative can present a Narrative-Unit scene where it strengthens the account, but the two are authored, validated and versioned as separate first-class objects."
  - "**Reuse across the stack.** EM Narrative composes existing infrastructure rather than adding a parallel one: the Shelf / acquisition pipeline (documents, images), Heriverse / ATON (3D embeds), the matrix / epoch machinery (DP-12 / DP-34), the paradata chain (DP-66), propagative author / license / embargo metadata (DP-32) and multilingual labels (DP-63). The addition is one concept — the NarrativeNode and its embed grammar — plus the four output projections."
  - "**RDF / SPARQL surface** opened by treating the narrative as a node: *list all narratives that cite a given US ordered by block position*; *list narratives whose embeds reference a now-retracted source*; *trace which paradata chains a narrative renders as evidence*; *count narratives per Activity / Epoch to measure the interpretive coverage of a project*; *find reconstructions that have a 3D scene but no authored narrative*. Maps to the RDF export layer once the NarrativeNode is declared in the EM ontology."

**Build status — 2026-08-22.** EM Narrative is built and measured live, end to
end. The NarrativeNode, prose-plus-embed blocks and the site-story scaffolder
exist in s3Dgraphy; EMStudio authors the narrative (a palette, drag-to-embed, an
AI draft that arrives attributed and is human-validated); and all four
projections — **HTML, Word, LaTeX and Jupyter** — export with the live figures
baked in (the Harris matrix, the vector map, the timeline). It is the technical
proof behind the Heritage *"Who Made This?"* paper. What remains is the
publishing front — baking the outputs to the Extended Matrix Catalog and the
triplestore — and step-by-step authoring polish. The design below is the target;
the substrate now stands.

Extended Matrix has spent a decade making the *evidence* of a reconstruction auditable: every virtual stratigraphic unit, every reconstructive claim, every documentary source behind a property. What it has never had is a native way to **tell the story of that reasoning** — an authored document that walks a reader through *why* a reconstruction looks the way it does, with the matrix, the 3D scene, the sources and the uncertainty all present as live, citable objects rather than as flattened screenshots pasted into a word processor. EM Narrative is that missing layer: a first-class semantic-narrative object that interleaves authored prose with live references to the EM graph, so the account and the evidence never drift apart.

The design comes from a deliberate comparison. Mature CIDOC knowledge platforms already offer an excellent prose composer that embeds live knowledge-graph resources — maps, IIIF images, diagrams, charts, timelines — updated automatically as the underlying data changes. Two things they do not do: they store the authored document as an opaque HTML blob, so only the referenced resources stay queryable and never the composition itself; and they carry neither stratigraphy, nor time, nor 3D. EM Narrative keeps the good idea and moves the substrate to where EM has depth the comparators lack. The narrative becomes a **node in the graph** — projected to RDF, versioned, DTC-traceable — and its embeds can render the Harris matrix, an epoch slice, a US with its existence certainty, a representation model, a source-criticism chain, and an in-line 3D scene from Heriverse or ATON. The reasoning and the uncertainty of a reconstruction become first-class citizens of the story, not an appendix to it.

Concretely, a NarrativeNode is an ordered sequence of blocks: prose blocks holding authored text, and embed blocks that reference an EM resource by stable ID plus a view-type that decides how it renders. Because embeds are references rather than copies, a narrative can never silently fall out of step with the reconstruction it describes — change the US, and the narrative reflects it. The view-types are where the depth lives: matrix and epoch slices; 3D scene embeds; US / USV / proxy with certainty; representation models; documents and images through the Shelf and acquisition pipeline (IIIF where warranted); maps, timelines, tables and live queries over em.json; the paradata / source-criticism chain rendered **inside** the prose as an evidence trail; and — composable, not merged — a Narrative-Unit scene from DP-29 where a performative moment strengthens the account.

The narrative is authored once and projected to the audience's format rather than re-authored per output. The **dynamic web viewer** renders prose with live embeds, including in-line 3D — the reference implementation of the StratiGraph T6.3 dissemination layer that today is missing, and more than the comparators offer because it brings stratigraphy and 3D into the narration. A **smart LaTeX** projection resolves embeds to figures, matrix diagrams, evidence tables and citations for scholarly print. A **semi-static docx / HTML** projection produces a self-contained snapshot for reviewers, reports and deliverables. And a **Jupyter-notebook** projection resolves embeds to live s3Dgraphy queries and generated figures, so a computational reader can re-run the analysis behind the prose. That last target is not a new direction for the EM horizon so much as a generalisation of one already sketched: DP-21 (EM Meter) and DP-13 (Virtual SU Sheet) already reached for Jupyter as an *analytics* surface over the graph; EM Narrative carries prose, evidence and reproducible computation in the same notebook, turning analysis-only notebooks into narrative ones.

Authoring happens in the EMStudio 2D web editor — a prose editor plus drag of resources from the graph or the Shelf to create embeds, the same gesture a mature platform offers but operating on em.json rather than on triples or on an HTML document. The two-tier discipline is preserved end to end: the narrative is authored in the property graph and projected to RDF as an information object with reference predicates, never authored triple-first, so merge-by-UUID stays intact. This is the positioning that matters: EM Narrative is native and sovereign. The aim is not to depend on an external platform but to own the authored-narrative surface precisely where EM's depth — stratigraphy, uncertainty, 3D, RDF-first — is the differentiator. Interoperability with mature external knowledge platforms remains a separate and purely technical opportunity, not a dependency this feature is built around.

Two clarifications keep EM Narrative distinct from its neighbours. It is **not** DP-29 (EMN / Narrative Units): DP-29 formalises *what was lived inside what was built* — dialogues, ritual acts, characters as USV, the four-axis performative schema — while EM Narrative is the documentary account of *how the reconstruction was reasoned and proven*. A DP-29 scene is simply one of EM Narrative's embed view-types; the two are authored and versioned as separate first-class objects, composable but not conflated. And a naming note: *EM Narrative* names the authored object, a term kept deliberately because it is the clearest available. The runtime that **plays** a narrative — the dissemination viewer — is a distinct thing that may deserve its own disambiguated name (*storyline* has been floated), though the working assumption is that context disambiguates *narrative* well enough that a separate coined term may prove unnecessary. That decision is left open, and it does not block the model.

**Output, publication and language (2026-08-03 direction).** The multi-output projection is not a nicety but the destination: each format is produced by **baking** the live views — images embedded, maps rendered static, links resolved — so the same narrative reaches a **LaTeX** print, a **Jupyter** notebook, a **DocX** document (essential for the ordinary user, not only the scholar) and **static HTML**. The baked outputs land on the **Extended Matrix Catalog** and, through the RDF projection, in a **triplestore** from which they can enter a Heritage Digital Twin at any time — carrying, unlike a plain HDT, the *validated reasoning* itself. Language runs on two rails, matching EM's label/content split: **labels** are multilingual and interchangeable (the DP-63 mechanism — the same node, filled in any language), while **content** is marked in the language it was authored in and can be **translated by the AI and then validated**, with the translation recorded in the narrative as a first-class generate-then-endorse act — exactly the mechanism used for authored prose. Image **captions** are the same: AI-derived from the text, human-validated. The project's languages are English, Greek, Hebrew, Italian, Spanish, Polish, Romanian and French (Hebrew right-to-left), and the EMStudio interface is localised across them so that authoring in any language is authoring the same graph. See DP-63 for the label rail and DP-80 (StratiMiner) for the sibling assisted-authoring tool; every AI act across prose, translation, captions and extraction passes through one seam: generation attributed, human validation, recorded in the graph.
